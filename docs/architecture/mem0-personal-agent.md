# Mem0 OSS 与个人代理的第一阶段

Dao 的长期方向是理解用户目标、偏好和判断方式的个人代理。本阶段将长期记忆的存储、语义召回和历史记录接到 **Mem0 开源 Node SDK (`mem0ai/oss`, 3.3.1)**，保留当前编码代理的执行能力。没有接入 Mem0 托管 API，也没有引入 Zep/Graphiti。

## 启用

1. 将 `docs/examples/mem0.json` 复制到 `~/.dao/mem0.json`，或通过 `DAO_MEM0_CONFIG` 指向自己的配置。
2. 配置 embedding 服务。示例使用 OpenAI 协议，`DAO_EMBEDDING_API_KEY` 从环境变量读取；API 地址、模型和 `dimension` 必须匹配。支持兼容该协议的自建服务，包括提供 `/v1/embeddings` 的 Ollama；此时填写本机 URL、实际模型及其维度。不要把凭据提交到仓库。
3. 启动 Dao，`/memory` 应显示 `Mem0 OSS`。可设置 `DAO_MEMORY_BACKEND=mem0` 强制启用；缺少配置或配置无效会报错。
4. 在各旧项目中执行一次 `/memory import`，导入其项目记忆及用户、知识库记忆。迁移记录让重复执行跳过已导入条目；已在 Mem0 删除的条目不会因重复导入而复活。原 Markdown 文件保留。
5. `MemoryRead` 支持自然语言语义查询，也支持按 ID、旧名称或标题精确读取。`/memory delete <ID>` 删除指定条目。迁移后当前会话可按需读，新会话重新生成固定注入内容。

没有配置时保留文件兼容模式，避免现有安装因缺少 embedding 服务无法启动。`DAO_MEMORY_BACKEND=files` 可显式切回文件模式；两套存储不双写，切回后不会自动拥有 Mem0 期间的新记忆。`--no-memory` / `--eval` 不初始化后端、不会迁移或写入记忆。配置或调用失败不自动回退到另一个后端。

`llm` 可选，格式与 `embedder` 相同；默认继承 Dao 当前模型的 OpenAI 兼容配置。本阶段已提炼的记忆使用 `infer:false`，不会为了保存事实额外调用 Mem0 的提取模型。自动提取仍由 Dao 的 `--reflect-memory` 开关控制，默认没有扩大后台提取范围。

## 持久化及作用域

- `~/.dao/mem0/vectors.db`：SDK 本地 SQLite 向量库，跨进程重启保留。
- `~/.dao/mem0/history.db`：Mem0 的正文新增、更新、删除历史。
- `~/.dao/mem0/embedding.json`：不含凭据的向量配置指纹。更换模型、服务地址或维度时拒绝混用已有向量，需要备份并重建向量库。
- `~/.dao/mem0/import-ledger.json`：按用户身份及原始文件路径记录导入进度。

`userId` 表示同一个人，跨项目和子代理共享；`project` 同时按真实工作区绝对路径的摘要隔离，两个同名目录不会串库。移动仓库会形成新的项目身份，需要重新导入或另行迁移。子代理继承主会话后端，临时 worktree 不切换记忆身份。

`user` 和 `knowledge` 是用户全局的两个命名空间；`project` 是项目命名空间。知识库启动注入继续保留旧的 `origin/locked` 过滤，按需检索则可查询用户自己的跨项目知识。`scope` 显式指定优先于类型路由。删除推荐使用 ID，旧名称可能匹配多个作用域。

默认关闭 Mem0 遥测（显式设置 `MEM0_TELEMETRY=true` 可覆盖）。本地存储不等于所有计算本地：写入正文与检索问题会发往配置的 embedding 服务，只有配置本机服务时这部分也留在本机。

## 接入边界

`MemoryBackend` 是 Dao 的边界，工具、启动注入、反思持久化和 `/memory` 使用同一实例。文件后端是兼容适配器；Mem0 后端负责真实 SDK 调用。Mem0 不直接暴露到工具 schema 或代理执行循环中，后续可以增加图谱适配器。

Dao 继续负责：

- 提取值得保存的内容，保留 `type/confidence/source/origin/locked` 与适用上下文。
- 显式纠正和确认，防止把一次选择泛化成永久偏好。
- 防止凭据写入正文或元数据。
- 会话开始固定注入和按需读，保持前缀缓存机制。

Mem0 负责：

- 本地向量存储与自然语言召回。
- 按用户/项目命名空间过滤。
- 正文变更历史。

使用 `infer:false` 是有意的第一阶段边界：Dao 已经提炼了事实，再提取一次可能丢掉理由、条件和来源。因此本阶段没有启用 Mem0 自身的自动事实提取/语义合并；同名更新仍采用确定性身份匹配，语义合并由 Dao 反思器明确提出。Mem0 模式不运行旧文件库 GC 和后台 consolidate，也不会宣称已经实现自动遗忘或完整时间知识图谱。

本地适配器在单个实例内串行写入；SQLite 负责文件层并发。多个独立 Dao 进程对同一记忆的读改写还没有跨进程事务保证，这是后续多会议室共享记忆需要补齐的边界。当前本地向量实现面向个人规模，查询会扫描本地数据，不适合作为无限规模服务。

删除条目后不会再被召回，但 Mem0 历史数据库保留变更记录，旧 Markdown 备份也仍存在；`delete` 不等于所有副本的隐私擦除。

## 个人代理后续阶段

| 阶段 | 要解决的问题 | 验收依据 |
| --- | --- | --- |
| 本阶段：记忆基础 | 跨会话记住、相关时召回、纠正旧偏好、隔离项目 | 持久化、语义召回、作用域、纠错、删除及迁移测试 |
| 决策案例 | 用户为什么接受/拒绝某个方案，成立条件是什么 | 同类新场景能引用真实案例，不能把不同原因合并成行业偏好 |
| 判断原则 | 从案例提出可审查的原则，区分明确表达与推断 | 原则有来源、反例、置信度，用户纠正能更新依赖案例 |
| 目标与授权 | 连接长期目标、当前任务、进度、条件和行动许可 | 目标变化能修正计划；记忆中的愿望不能自动转化为执行授权 |
| 时间关系 | 判断何时变化、决定依赖哪些前提、哪些关系失效 | 建立带时间的回归集，再决定是否引入 Graphiti |

先用真实交互建立“有无记忆”的对照评测，再决定扩展复杂度。存储条数、检索命中率不等于代理更懂用户；最终指标是任务决策是否更符合用户意图，以及错误记忆造成的负面影响。

## 验证

- `npm run typecheck && npm run lint && npm test`
- `npx tsx scripts/verify-mem0.ts`：真实 SDK + 本地模拟 embedding + 临时 SQLite。
- `bun scripts/bundle.ts --entry scripts/verify-mem0.ts --outfile /tmp/dao-mem0-smoke`，再在仓库外运行该二进制，验证 Bun 内置 SQLite 接线。
- `npm run bundle`：构建正式单文件；发布工作流也使用相同构建入口。

专项测试不使用真实凭据，不读取用户现有记忆，不代表已验证远程模型的实际检索质量。
